# 用户偏好档案（PREFERENCES.md）格式规范

图库根目录下的 `PREFERENCES.md` 记录**跨条目的个人审美与习惯**，是实现"图库越长越像你"的核心载体：各条目记录原文献的客观绘图范式，本档案则记录复用过程中反复作出的主观选择。二者职责独立，严禁混淆混写。

## 两层结构：整体偏好 ↔ 部分偏好

偏好沉淀于两处不同载体；其归属判定标准取决于**适用范围**，而非存储位置本身：

| | 整体偏好 | 部分偏好 |
|---|---|---|
| 位置 | `library/PREFERENCES.md` | 各条目 `figure.md` 的「复用要点」「演化记录」 |
| 管控范围 | 跨图型的稳定习惯：配色体系、导出规格、英文/字号约定、统计标注方式等 | 仅服务于单张图或特定图族的结论：某图的列名映射、某图型的阈值习惯、某变体的已知问题 |
| 读取机制 | 每次复用时均默认读取（`retrieve.py` 输出包含稳定偏好） | 仅在命中对应条目时读取 |

二者存在动态迁移机制，**定期整理**（详见下节）即执行迁移的具体过程：当某条规则在多个条目中反复出现，应晋升为整体偏好；若某项整体偏好仅服务于单一图型，则当下沉回对应条目。层级划分失当将直接影响复用效果：滞留于局部条目的通用规则，在复用其他图表时无法生效；而误升至整体层级的局部规则，则会对所有图表产生干扰。

## 定位与边界

- **读**：在模式 B 检索与实例化阶段为必读项（`retrieve.py` 输出已包含稳定偏好）。优先级顺序为：用户**当前指令** > 稳定偏好 > 条目缺省——仅在用户未显式指定的维度，方以稳定偏好予以填充
- **写**：仅记录**可观察到的偏好信号**，严禁主观推断。合法的偏好信号分为三类：①用户在适配过程中明确给出的选择（"阈值用 1.5""别用红色"）；②交付后的反馈评价（"很好用"/"图例放上面"）；③用户主动声明的长期习惯（"以后导出都要 PDF"）
- **与 figure.md 的分工**：仅适用于单张图表的特定适配结论写入该条目的「复用要点」；跨条目通用的习惯（包括阈值、配色、字体、尺寸、导出规格及高频图型等）方可归入本档案。写入本档案时，若发现关联条目的复用要点需同步修订，应一并更新处理

## 项目级风格一致怎么落地（重要）

在同一项目内维持跨图表风格的一致性（涵盖色板、主题、尺寸与导出规格），本质上属于**偏好问题**，而非代码问题：

- 将相关结论记入 `PREFERENCES.md` 条目时，**必须标适用范围**（`〔适用范围：uc-cart 项目〕`）；因其仅适用于特定项目，而非全图型通用的全局偏好
- 绘图阶段严格依照偏好执行。每个绘图脚本及条目模板应保持**自包含**，切忌为追求脚本一致而引入共享 theme 或公共依赖文件，否则会破坏脚本与条目的独立性及可移植性
- 风格一致性仅需在实际执行对应项目任务时按需保证：将该项目使用的色板与尺寸按项目记录为一条限定适用范围的偏好，绘图时据此执行即可；无需为此开展工程化的统一重构，亦不要引入共享 theme 文件导致脚本相互引用

## 文件结构

```markdown
# 用户偏好档案

（由 agent 在复用交付后自动追加；两类条目：稳定偏好 ≥2 次一致才晋升，单次观察仅备查）

## 稳定偏好
- 显著性阈值：padj<0.05 且 |log2FC|>1.5 〔2026-08-29 火山图任务，2026-09-12 差异热图任务，2 次〕
- 导出规格：300dpi PNG + PDF，宽 ≤6 英寸 〔2 次〕

## 单次观察
- 2026-08-29 〔U1 火山图〕要求数值标签只标 top8，未说是否通用——待复现确认

## 整理记录
- 2026-09-28 整理：晋升 2、合并 3、降级 4、清退 2、下沉 1
```

## 规则

1. **晋升**：设置两条并列通道——① 同一条偏好在「单次观察」中累计记录 ≥2 次且互不矛盾；② **用户显式声明为通用规则**（"以后都要…""这是通用要求"）。满足条件者移入「稳定偏好」，并注明累计次数与日期；按通道 ② 晋升时，须在标注中写明"用户显式声明为通用规则"，解析脚本据此免除重复出现次数的要求
2. **冲突**：当新观察到的偏好与既有稳定偏好相抵触时 → 以最新记录为准，将旧偏好移回单次观察并注明被推翻原因
3. **格式**：每行统一采用 `偏好内容 〔日期 场景，次数〕` 格式；场景处填写简短任务描述即可。**每行必须带日期与次数**——整理流程依赖二者判定条目的晋升、降级与过期状态，缺失标注的行将被 `review_preferences.py` 直接报错拦截（用户显式声明的规则同样须附带日期，次数记为 1 即可）
4. **容量**：稳定偏好规模应保持在 ≤15 行（达 ≥13 行即应启动合并或下沉），单次观察应保持在 ≤20 条（达 ≥18 条即应启动清理）；指标超限即表明亟需执行整理
5. **范围标注**：仅适用于特定图类的规则，写入档案时必须标出适用范围（`〔适用范围：热图〕`）；未标明范围者默认视为全图型通用。此环节极易产生疏漏，须严格核查
6. 本文件属于**个人数据**：默认由 .gitignore 排除在公开仓库之外；若使用私有同步仓库，则随代码库一并同步

## 整理流程（定期）

偏好是在实际复用中动态积累形成的；若缺乏定期整理，容易出现重复行堆积、已失效规则滞留于稳定偏好、局部规则误泛化为通用规则，以及跨条目高频规则未能及时晋升等问题。**触发条件与节律**（参见 SKILL.md「偏好整理」节）：每次完成模式 A/B 交付收尾时执行一次

```bash
python3 <技能目录>/scripts/review_preferences.py --check    # 退出码 1 = 该整理了
```

到期条件（由脚本自动判定）：距上次整理 >30 天、稳定偏好 ≥13 行、单次观察 ≥18 条、自上次整理新增 ≥8 条演化记录，或出现容量、格式及升降级异常。跨条目复现仅作为"考虑晋升"的提示，不计入到期判定条件。

### 五步

0. **通读**：校验脚本仅能捕获字面近似与硬指纹 token（长度 ≥5 的代码 token）。对于同一语义的不同表述（如"热图 cell 要正方形、不留空隙"与"热图格子必须正方形且无缝隙"），须依赖人工通读识别。脚本未引入模糊匹配机制，系因领域词的高重合度无法有效区分诸如"生信图默认用英文"与"生信图默认只导 PDF"等共享主语前缀的语句，此类误报极易诱导模型误将两条不同的规则合并
1. **晋升**：凡经用户显式声明为通用规则，或在单次观察中累计记录 ≥2 次且内容一致者 → 移入稳定偏好，并累加记录出现次数与对应日期
2. **合并**：将表述同一含义的多行合并为一条，同时保留所有历史日期（确保演化证据不遗失）
3. **降级/推翻**：稳定偏好中仅出现 1 次或已被最新反馈推翻的条目 → 降回单次观察，注明调整原因
4. **下沉/清退**：仅服务于单一图型或特定项目的偏好 → 下沉至对应条目的「复用要点」；超过 >60 天未再复现的单次观察 → 执行清退

### 候选从哪来

除在交互中即时写回外，还须定期检索会话历史以挖掘用户的纠偏反馈（"再改/还是不对/不要/改成"）：

```bash
python3 <技能目录>/scripts/mine_feedback.py --since <日期> --min-count 2
```

产出 `<图库>/FEEDBACK-CANDIDATES.md`（按频次聚类排序的用户原始表述及对应日期），且**只产出候选**。随后须逐条研判归属：跨图型通用规则 → 稳定偏好；仅服务于特定项目或图型者 → 下沉至对应条目并标注适用范围；单次临时要求 → 直接舍弃。

### 报告怎么用

- 执行 `review_preferences.py`（不带参数）将生成面向人类可读的巡检报告，涵盖：必做项、跨条目复现、条目内堆积、过期单次观察及疑似冲突条目
- 添加 `--json` 参数可输出机器结构化数据供 agent 逐项解析执行；`--top N` 用于限制各小节展示的条目数量
- 脚本执行遵循**只读不写**原则：语义层面的合并必须由 agent 自行判断并落笔，以防自动化操作误损个人数据
- 整理完成后，须在 `## 整理记录` 追加一行：`- YYYY-MM-DD 整理：晋升 N、合并 N、降级 N、清退 N、下沉 N`；脚本据此判断下一次整理的到期时间
- 凡修改过任意 `figure.md` 后，均须运行 `scripts/build_index.py` 重建索引
- 定量统计指标（条目数、命中率、未命中需求）交由 `scripts/summary.py` 负责采集；偏好整理仅聚焦于偏好本身，二者在交付收尾时统一执行 `--check` 校验

### 条目侧的整理

「部分偏好」同样存在信息冗余堆积的问题：当某个条目经历反复迭代后，「演化记录」常会残留大量已被取代的中间结论。整理时应一并处理：

- 仍然生效的缺省配置 → 收敛进「复用要点」，演化记录仅保留"改了什么、为什么"
- 单条目的演化记录达到 ≥5 条时（脚本将报告"条目内堆积"）→ 表明该执行一次折叠
- 删除条目时，须同步清理其他条目 `related` 字段中指向该条目的引用（否则 `build_index.py` 将触发告警）

### 与 harness 原生记忆的同步（防漂移）

若同一份偏好规则并存于两处载体（例如 omp 的 `managed-skills/*` 或项目上下文记忆中的绘图约定副本），极易导致规则偏离与状态不同步：若更新了 `PREFERENCES.md` 却遗漏该副本，后续会话便会依据陈旧规则执行绘图。整理时：

1. 运行 `python3 <技能目录>/scripts/review_preferences.py --digest` 生成一份紧凑摘要（包含稳定偏好、可选的单次观察及一行检索提醒声明）
2. 利用该摘要刷新 harness 记忆层或托管技能中的副本，或直接删除副本并替换为指向 `PREFERENCES.md` 的指针（推荐采用后者，以确保单一事实来源）
3. 摘要内附带的"画图前先跑 retrieve.py"声明，可同步补齐绘图前置触发钩子（详见 `references/trigger-hook.md`）

## 由 init_library.py 生成骨架

新图库在初始化阶段会自动创建包含上述结构注释的空档案；现有图库若缺失此文件，须参照本规范补全。若既有档案缺失 `## 整理记录` 节，在整理时补齐对应小节即可（脚本本身不执行文件写入操作）。
